## 0. 一句話

做一個 **個股深度審視為主、完整盤勢總覽為輔** 的個人用財經網站，參考 Fugle AI 個股頁（`fugle.tw/ai/2330`）與 futures-ai 盤勢總覽（`alpha.futures-ai.com/market-overview`）；桌面為主、手機可用（RWD + PWA）。**前端全新，資料/AI 沿用既有「財經APP」的 engine + gateway，缺口才補新端點。**

## 2. 架構

```
瀏覽器 (review-web, Vite+React, PWA)
        │  只打 /api（絕不直連 engine）
        ▼
Node gateway  server.cjs + routes/   ← 既有，本案會新增 /api/market/* 等端點
        │  代理 / 組合 / 降級
        ▼
Python engine  FastAPI :8000         ← 既有，本案會新增 /data 或 /market 端點吐原始/聚合資料
        │
        ▼
資料源：FinMind / 富果 / yfinance / TWSE MIS / TAIFEX / FRED / 新聞   ← 全部沿用
```

原則沿用既有系統鐵律：
- 前端**只打 gateway `/api`**，不直連 engine、不重算數字。
- gateway **只組合/轉發/降級**，數字一律吃 engine 與 `reports/`。
- engine 掛掉要 **graceful degradation**，不假裝成功。

## 7. 沿用既有系統的坑（務必帶進每階段 review）

- 老王報告 **emoji 與股市相反**：🔴=看多 / 🟢=看空 / 🟠=中性觀望（與股市紅漲綠跌相反）；`/api/reports` 是 raw markdown，前端勿反向上色。
- 型別分歧：`water_level` float 0~1（另有中文 `water_level_text`）、`puhui_sentiment.score` 0~100。
- K線**預設還原價**（`ohlcv?adjust=1`）；未還原源對除權息/分割股（如 0050）會斷點失真。
- 分K/內外盤需 `FUGLE_API_KEY`（已設）；未設要優雅降級不破圖。
- `agents/decide` **很貴**，只前端明確觸發、別放進首頁或個股自動載入。
- engine 掛掉要 graceful degradation（沿用既有降級語意）。
- 不動既有 `web/`、不改壞 `puhui_daily.cjs`、不重接資料源。
- 電子/金融指數折衷：首頁表頭資料為官方指數即時值（`t13`/`t17`），但走勢圖（Sparkline）採用 ETF 還原線（`0053.TW`/`0055.TW`），漲跌幅與走勢形狀可能存在微幅背離。
- 台指期 (TX) 走勢圖：分時與歷史走勢圖由加權現貨 `^TWII` 按比例線性縮放 (Trend Scaling) 生成，具有 `intraday_proxy: true` 標記。
- 🚨 TWSE MIS 回傳的 `ch` **無 `tse_`/`otc_` 前綴**（`t13.tw`），但 `MIS_CHANNELS` 的查詢值**帶前綴**（`tse_t13.tw`）→ 任何拿 `MIS_CHANNELS` 值去 join MIS 回傳（如 sectors 漲跌幅）查表前**必須 strip 前綴**，否則永遠 miss 並靜默落 `0/null`（Phase 1 sectors 全平盤 bug 根因，已修）。

- **2026-07-14 TAIEX 收盤資料卡在 07-09、市場狀態燈號讀到 5 天前的收盤（engine bug 修復，commit `f4714e9`）**：使用者截圖回報——`/rebalance` 的「TAIEX 市場狀態燈號」顯示「自 2026-06-22 高點 47,742 回撤 5.00%（目前收盤 45,355，統計截止日 2026-07-09）」，但當天 Google 加權指數是 44,737.95。**查證**：VM 上 curl gateway `/api/stocks/TAIEX/ohlcv`，最後一筆確實是 07-09 = 45,354.61（燈號忠實反映後端，數字沒算錯，是資料本身停住）；對照 0050 同一 FinMind 來源卻有 07-13、07-14 → 非來源故障。**根因**在 `engine/app/data/cache.py` 的 `get_timeseries`：涵蓋浮水印（`data_cache/ohlcv/{code}.meta.json` 的 `covered_end`）**一律推進到「本次請求的 end」，即使該次補抓回傳空的**。原設計用意是「空回傳＝假日，標記已抓過、下次命中，週末不重打 API」，但盤中/EOD 未出時查詢也會回傳空 → 該交易日被永久標記為已涵蓋 → 之後每次 `end=今天` 都判定 cache hit、再也不回補。實測 `TAIEX.meta.json` 宣稱 `covered_end: 2026-07-14`、parquet 卻自 07-11 00:41 起未再寫入。**TAIEX 是唯一中招的標的**——只有它每次開啟再平衡頁都以 `end=今天` 查詢，浮水印才會天天往前推、逐日越過尚未出 EOD 的交易日；其他標的（0050 另有每日 pipeline 主動重抓）浮水印停在上次查詢日，下次自然形成缺口補回。**修法**：區分「已結算／未結算」——已結算日期（≤ 今天 − `_SETTLE_GRACE_DAYS`=3）的空回傳仍視為假日照舊推進浮水印（維持原本不重打 API 的設計）；未結算窗內浮水印上限收斂到「實際抓到的最後資料日」，讓來源補上後仍視為缺口回補。**測試**：新增 `test_lagging_source_day_is_not_skipped_forever`（反證過：grace 設 0＝修復前行為時，日期由 07-09 直接跳到 07-13、中間日被永久跳過）＋`test_settled_weekend_tail_still_cache_hits`（防止修過頭變成每次重打 API）；`test_cache.py` 6/6 全過。全套 79 passed / 2 failed，該 2 項（`test_fundamentals`、`test_market_capital_tide_ok`）為打外部即時資料的既有失敗，已 stash 改動跑 baseline 確認訊息逐字相同、與本修改無關。**部署**：VM pull ＋ `systemctl restart puhui-engine`（engine 程式碼有改，非純前端）。**注意——修復只防新發生、不會自癒既有卡死**（`covered_end` 已超前 → 無缺口 → 不觸發補抓 → 浮水印永不重算），故另手動將 `TAIEX.meta.json` 的 `covered_end` 收斂回 `2026-07-09` 解卡（備份 `TAIEX.meta.json.bak`），觸發補抓 `fetched_ranges: [[2026-07-10, 2026-07-14]]` → 補回 07-13 = 45,380.52、07-14 = 44,737.95（與使用者 Google 截圖數字吻合），浮水印回到正確的 07-14。**已掃描全部 13 個快取**：另 7 個浮水印超前者（2317/2330/2454/3081/3189/2449/6435）逐一核對日曆，超前部分只跨週末與 07-10 休市日，未越過任何真實交易日＝良性，無需處理。**驗收**：燈號現為「自 2026-06-22 高點 47,741.51 回撤 6.29%（目前收盤 44,737.95，統計截止日 2026-07-14）」、仍為「正常」（tier1 = 10%）。**教訓**：此燈號是股災偵測器，今天回撤 6.29% < 10% 故結論未受影響、不影響任何操作，但**急跌時落後數日正是它最不能失準的時候**；另注意 2026-07-10（五）為休市日，0050 同樣無資料，該日無資料屬正常。

- **2026-07-13「鎖定現金」誤把全部閒置現金都鎖住（bug 修復，commit `a803f6e`）**：使用者截圖回報——再平衡頁鎖定「現金保留額」（例：閒置現金 $1,597,363、保留額 $150,000）後，超出保留額的 $1,447,363 閒置現金也一併被排除在再平衡建議之外，無法拿去加碼 00631L 或債券。**根因**：opt19 資產鎖定機制把 `locked.cash` 實作成「凍結當下整包 `cash`（閒置現金總額）欄位」，但 UI 標籤寫的是「鎖定現金保留額（固定保留、不投入債券）」——**UI 標籤與底層計算語意不符**，`cash` 是閒置現金總額、`cash_reserve` 才是使用者想保護的保留額子集。**修法**：把現金鎖定重新定義成「保護下限」而非「原地凍結」——`lib/rebalance.ts` 的 `allocateDefensiveWithLocks`＋`computeRebalance` 改成只保護 `min(閒置現金, cash_reserve)`，超出保留額的部分正常參與再平衡；連帶移除「現金＋債券全鎖定→00631L 完全凍結（連賣出都擋）」的特例——賣出 00631L 的價金本來就能流入現金（鎖定只設下限、不設上限），既有的 headroom／shortfall 公式本身就能正確處理全鎖定邊界案例，不需要額外分支。`rebalanceLock.test.ts` 4 個受影響案例（3a/4/6/7）逐一手算重新驗證，並新增 6b/7b 兩個直接對應使用者回報情境的回歸測試（即使兩檔債券都鎖定，超額閒置現金仍能精準買到目標 β；鎖定現金不擋賣出方向）。vitest 119/119 全過、`npm run build` 乾淨。純前端零後端零路由改動（`routes/rebalance.js` 白名單透傳與 `rebalance_alert.cjs` 皆不涉及此鎖定計算邏輯）。VM 部署（pull+build，免重啟 gateway）chunk hash 與本機 build 逐位元一致、curl 驗證 `/review/` 200。UI 同步補上說明文字（鎖定按鈕 title＋現金保留額欄位下方提示＋「整體邏輯」分頁條目）講清楚「鎖定只保護保留額本身」。
